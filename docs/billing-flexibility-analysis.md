# Анализ гибкости биллинга

## Текущая архитектура (кратко)

```
Period → Services → REGULAR invoice → Claims (строки счёта) → Payments
                                              ↑
                                     RecalcClaimsPaidCommand
                                     распределяет оплату по claims
```

Каждый участок получает один REGULAR-счёт за период. Claims создаются автоматически из услуг периода + мигрированные долги. Оплата распределяется алгоритмически.

## Жёсткие точки

### 1. Payment distribution негибкий

`RecalcClaimsPaidCommand` всегда раскидывает всю сумму платежа по всем claims в порядке сортировки ServiceTypeEnum. Нельзя:
- направить платёж на конкретную услугу
- зарезервировать часть платежа под конкретный claim
- установить приоритет погашения (сначала штрафы, потом основной долг)

### 2. Отрицательные суммы ломают алгоритм

Скидка/штраф отрицательной строкой счёта (claim с cost < 0) разбивает payment distribution:
- `remaining` становится немонотонным
- цикл может выйти на advance при нулевом остатке
- суммы на уровне claim'ов и invoice не сходятся

Единственный способ — отдельная услуга «Штраф» или «Скидка» с положительной стоимостью.

### 3. Услуги привязаны к периоду, а не к участку

`MEMBERSHIP_FEE` гибок (берёт `accounts.size` на момент генерации). Но `TARGET_FEE`, `PERSONAL_FEE`, `ELECTRIC_TARIFF` — фиксированная сумма/тариф на всех. Нельзя задать персональную стоимость услуги для конкретного участка без создания отдельной услуги.

### 4. Advance и DEBT завязаны на ServiceTypeEnum

`getAdvancePayment()` ищет `ADVANCE_PAYMENT`. `getDebts()` ищет `DEBT`. Поведение нельзя переопределить или расширить без правки core.

### 5. Один REGULAR-счёт на участок за период

Нельзя разбить на несколько (например, членские взносы и электричество — разными счетами). Нельзя объединить участки одной семьи в один консолидированный счёт.

### 6. Нет пролонгации услуг между периодами

Каждый период услуги и claims создаются заново. Нет механизма «автообновления» подписки.

## Резюме

Система заточена под стандартный workflow: тариф × площадь = сумма → счёт → оплата. Хорошо работает для типовых СНТ. Негибка, когда нужно:
- ручное назначение платежа
- скидки/штрафы
- персональные тарифы
- консолидация счетов
- рассрочка
