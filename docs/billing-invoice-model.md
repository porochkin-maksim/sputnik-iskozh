# Billing Invoice Model

Этот документ фиксирует рабочую модель счетов в системе и правила, которые должны соблюдаться при рефакторинге billing-сценариев.

## Цель

Счёт должен отвечать на два вопроса:
- за какой период и для какого аккаунта он выставлен;
- к какой финансовой роли и, если нужно, к какой услуге он относится.

При этом:
- `REGULAR` не должен смешиваться с сервисными начислениями;
- электрические и иные сервисные начисления не должны плодить отдельный счёт на каждое событие;
- `ClaimEntity` остаётся атомарной строкой начисления.

## Базовые инварианты

1. `REGULAR` invoice
- Один `REGULAR` invoice на `account + period`.
- Используется для основных периодных начислений.
- Не обязан иметь `serviceId`.

2. `INCOME` / `OUTCOME`
- Используются для дополнительных финансовых документов.
- Могут быть привязаны к конкретной услуге через `serviceId`.
- Не заменяют `REGULAR`.

3. `serviceId` на invoice
- Связь с `ServiceEntity` должна быть необязательной.
- Нужна только там, где документ относится к конкретной услуге.
- Не является заменой `claim.service_id`.

4. `ClaimEntity`
- Одна claim-строка = одно начисление/одно событие.
- Claims не должны превращаться в агрегатор разных услуг.

## Рабочее правило для выбора счета

При создании или поиске invoice для сценария нужно учитывать:
- `accountId`
- `periodId`
- `type`
- `serviceId`, если он задан

То есть для сервисных начислений поиск должен быть не только по типу, но и по услуге.

## Электричество

Для `CheckClaimForCounterChangeCommand` электричество должно жить отдельно от `REGULAR`.

Рекомендуемая схема:
- найти или создать invoice нужного типа для `account + period`;
- если начисление относится к конкретной услуге, связать invoice с этой услугой;
- добавлять новые counter-change события в тот же service-specific invoice, а не плодить документ на каждое показание;
- `REGULAR` не трогать.

## Что это даёт

- `REGULAR` остаётся чистым и предсказуемым;
- сервисные начисления получают явную предметную привязку;
- UI и экспорт могут показывать счёт не только как финансовый тип, но и как “счёт по услуге”;
- биллинговая логика перестаёт путать основную периодную модель и отдельные сервисные сценарии.

## Примечание по `account->isSnt()`

`account->isSnt()` остаётся важным бизнес-флагом для определения роли аккаунта в движении денег.
Но он не должен подменять предмет счёта.
Предмет счёта описывается типом документа и, при необходимости, `serviceId`.
