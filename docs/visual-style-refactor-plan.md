# Visual Style Refactor Plan

Цель: сделать сайт визуально более фирменным, цельным, спокойным и изящным без ломки текущих рабочих контрактов.

## 1. Что уже видно как проблемные зоны

- В `resources/sass/` есть смешение:
  - системных слоёв,
  - временных crutches,
  - page-level стилей,
  - компонентных стилей.
- В `resources/views/` много страниц уже стандартизировано по структуре, но визуально они всё ещё разнородны:
  - разные карточки и таблицы оформлены по-разному,
  - часть страниц держится на inline-стилях,
  - есть дублирование shell-паттернов между public/profile/admin,
  - юридические и сервисные страницы выглядят слишком “служебно”.
- В `resources/js/` визуальная логика тоже расползается:
  - часть UI живёт в общих `common/*`,
  - часть в `public/*`, `profile/*`, `admin/*`,
  - часть в feature-specific блоках с собственными таблицами, карточками и диалогами,
  - местами ещё остаются локальные стили и пропсы, дублирующие общие UI-паттерны.
- Основной фирменный цвет уже задан, но не везде используется как система.

## 2. Приоритеты

1. Привести в порядок shell-слои и общие visual tokens.
2. Унифицировать карточки, таблицы, формы и заголовки.
3. Сделать public-страницы более “воздушными” и цельными.
4. Упростить и осовременить admin/profile представление без потери плотности данных.
5. Убрать визуальные crutches и точечные inline-стили.
6. В `resources/js` свести UI-компоненты к единой design system и убрать локальные визуальные исключения.

## 3. План по `resources/sass/`

### 3.1. Разделить роли файлов

- `variables.scss` оставить единственным источником цветовых и размерных токенов.
- `common.scss` сократить до:
  - глобальных утилит,
  - общих layout-паттернов,
  - cross-page visual helpers.
- `layout.scss` оставить для общих shell-правил:
  - navbar/footer,
  - background,
  - общий page canvas.
- `form.scss` оставить только для типовых форм и состояний ошибок.
- `template.scss` и `crutches.scss` разобрать и либо:
  - перенести в целевые файлы,
  - либо удалить после миграции.

### 3.2. Ввести единый визуальный язык

- Стандартизировать:
  - radius,
  - shadows,
  - border tone,
  - spacing scale,
  - hover states.
- Сделать более последовательными:
  - `.card`,
  - `.table`,
  - `.btn`,
  - `.alert`,
  - `.badge`,
  - `.page-title`.

### 3.3. Переписать shell-стили

- Навигация сверху:
  - сделать аккуратнее высоту, отступы и активное состояние,
  - убрать ощущение “плоского bootstrap-стандарта”.
- Подвал:
  - довести legal-links до цельного блока,
  - унифицировать social-strip и footer spacing.
- Page canvas:
  - привести фон/контейнеры к одному ритму между public/profile/admin.

### 3.4. Систематизировать формы

- Перенести всё к единому виду:
  - отступы,
  - label weight,
  - focus ring,
  - invalid state,
  - help text.
- Отдельно выровнять:
  - auth forms,
  - public request forms,
  - admin edit forms.

### 3.5. Сократить crutches

- Найти и убрать:
  - `crutches.scss`-стили, которые уже живут дольше своей необходимости,
  - устаревшие миксины и локальные overrides,
  - визуальные костыли в пользу системных классов.

## 4. План по `resources/views/`

### 4.1. Shell-страницы

- Привести к единому визуальному ритму:
  - `layouts/app-layout.blade.php`,
  - `layouts/profile-layout.blade.php`,
  - `layouts/admin-layout.blade.php`.
- Для каждого shell определить:
  - ширину контента,
  - spacing вокруг main,
  - поведение footer,
  - правила для sticky nav/панелей.

### 4.2. Public pages

- Сделать более выразительными:
  - `pages/public/index.blade.php`,
  - `pages/public/contacts/*.blade.php`,
  - `pages/public/news/*.blade.php`,
  - `pages/public/help-desk/*.blade.php`,
  - `pages/public/search.blade.php`,
  - `pages/public/garbage.blade.php`,
  - `pages/public/files/index.blade.php`.
- Нормализовать:
  - hero/lead blocks,
  - request cards,
  - list pages,
  - service/category pages.

### 4.3. Legal pages

- `privacy`, `terms`, `personal-data-consent`, `payments-info`, `cookie`:
  - привести к одному спокойному типографскому стандарту,
  - уменьшить “простынность” текста за счёт ритма и акцентов,
  - сделать оглавление/sections более читабельными.

### 4.4. Admin pages

- Уплотнить таблицы, но сделать их чище:
  - лучше header hierarchy,
  - аккуратнее badges,
  - меньше визуального шума.
- Унифицировать карточки и панели:
  - admin dashboard,
  - users/accounts/billing/help-desk pages,
  - logs/queues/system pages.

### 4.5. Profile pages

- Сделать профиль более “личным” и менее таблицезависимым:
  - account summary blocks,
  - invoice/counter pages,
  - action groups.

### 4.6. Shared partials/components

- Привести к общему стилю:
  - `partials/public/*`,
  - `partials/profile/*`,
  - `layouts/partial/*`,
  - `components/*`.
- Особое внимание:
  - `page-title`,
  - `legal-links`,
  - `social`,
  - `request-card`,
  - `x-admin.card`,
  - `x-auth.*`.

## 5. План по `resources/js/`

### 5.1. Разделить уровни Vue-компонентов

- `resources/js/components/common/*`:
  - только переиспользуемые атомы и молекулы,
  - без доменной специфики,
  - без feature-specific layout.
- `resources/js/components/shared/*`:
  - общие блоки для нескольких зон,
  - например account/counter/summary widgets.
- `resources/js/components/public/*`, `profile/*`, `admin/*`:
  - только page-level и feature-level компоненты соответствующей зоны.

### 5.2. Устранить визуальную фрагментацию

- Найти компоненты, которые:
  - рисуют таблицы по-разному,
  - используют собственные кнопки/меню вместо общих,
  - имеют локальные alert/card/input-group паттерны.
- Перевести их на общие элементы:
  - `CustomInput`, `CustomSelect`, `CustomTextarea`, `CustomCheckbox`,
  - `ViewDialog`,
  - `LoadingOverlay`, `LoadingSpinner`,
  - `Alerts`,
  - pagination,
  - common form wrappers.

### 5.3. Причесать формы

- Привести к одному виду:
  - `public/requests/*`,
  - `profile/*`,
  - `admin/*` dialogs and edit forms.
- Убрать дубли:
  - разные ошибки валидации,
  - разные способы отображения ошибок,
  - случайные inline-отрисовки label/input blocks.

### 5.4. Привести таблицы и списки к общему ритму

- Унифицировать:
  - заголовки таблиц,
  - action columns,
  - compact columns,
  - sticky headers,
  - empty states.
- Для длинных списков:
  - единый pattern карточка/таблица/toolbar/filter.

### 5.5. Вынести визуальные helper-паттерны в общие компоненты

- Часто повторяющиеся куски:
  - toolbar,
  - header panels,
  - summary panels,
  - action groups,
  - dropdown action menus,
  - status badges,
  - empty states.
- Если повторяются в 2+ местах, делать общими.

### 5.6. Стандартизировать composables/runtime

- Проверить, что composables не тянут случайный UI-state и не смешивают доменную логику с view-деталями.
- Зафиксировать границу:
  - composable управляет состоянием,
  - компонент отвечает за внешний вид,
  - store отвечает за глобальный cross-page state.

### 5.7. Убрать остатки старого стиля

- Найти компоненты, где ещё остались:
  - тяжёлые inline-стили,
  - жёстко захардкоженные цвета,
  - нестандартные размеры кнопок и таблиц,
  - лишние wrapper div’ы.

## 5. Стандарты, которые нужно зафиксировать

- Любая новая page-level разметка должна сначала проверяться на наличие общего компонента/partial.
- Любая новая таблица должна использовать общий table style, а не локальную импровизацию.
- Любой новый card/block должен наследовать системные отступы, radius и shadow.
- Любой inline `style="..."` в blade должен считаться временным и выноситься в Sass.
- Любой цвет должен ссылаться на токены из `variables.scss`, а не быть случайным `#...`.
- Любой Vue-компонент, который влияет на визуальный язык, должен использовать общие `common/*` элементы, если они существуют.
- Любой повторяющийся pattern в `resources/js` должен быть вынесен в общий компонент или composable.
- В таблицах и списках кнопки действий унифицируются по смыслу:
  - `a.btn` или `router-link`-аналог используется только для навигации на отдельную страницу;
  - `button` используется для локального действия в текущем контексте: открыть диалог, сохранить, удалить, запустить импорт;
  - `dropdown` в таблицах не используется; вторичные действия выносятся в явные кнопки/ссылки в строке;
  - если действие одно и часто используется, dropdown не нужен, а кнопка/ссылка должна быть видимой напрямую;
  - если строка имеет primary action, она должна быть одинаково оформлена во всех таблицах: либо как компактная ссылка-кнопка, либо как небольшой action button, но не вперемешку.
- Любая ссылка, которая используется как action в таблице или панели действий, должна выглядеть как явный UI-элемент:
  - либо `table-link-firm` для ссылок,
  - либо `admin-action-btn` для кнопок;
  - `btn-link` и голый текстовый линк в action-колонках запрещены.
- Узкие технические колонки в таблицах должны помечаться `table-thin-column`, если это:
  - `id` / `№` / технический номер,
  - checkbox/select column,
  - action column,
  - file/history/receipt column,
  - любая другая колонка, которая должна быть сжата до содержимого и не раздувать таблицу.
- Унифицированный паттерн для всех таблиц:
  - `primary action` = один явный entry point в сущность;
  - `secondary action` = редкие или разрушающие действия, только если их больше одного;
  - `quick action` = короткое локальное действие без перехода;
  - `row click` не использовать как скрытую навигацию, если есть явная кнопка-переход;
  - в одной таблице один и тот же тип действия должен выглядеть одинаково во всех строках;
  - если у строки есть навигация и локальные действия, навигация должна быть визуально первой и стабильной;
  - если локальных действий больше двух, они собираются в один dropdown; если одно-два, лучше оставить отдельными кнопками;
  - destructive action по умолчанию не выносить наружу, если оно не основное.
- Нельзя делать `id` единственным или неявным кликабельным элементом строки, если сущность имеет более понятный человекочитаемый идентификатор:
  - primary action должен быть привязан к названию сущности, номеру участка, номеру счета или понятному label;
  - `id` можно оставить как технический текст, но не как основной anchor, если это ухудшает читаемость;
  - если у строки есть смысловой name/number/display label, кликабельным должен быть он;
  - `id`-ссылка допустима только когда `id` сам по себе является бизнес-идентификатором и это естественно для пользователя.
- Ссылки в таблицах визуально должны быть различимы по роли:
  - primary navigation в таблице оформляется как `a.btn btn-sm btn-outline-success` или аналогичная компактная link-button;
  - вторичные текстовые ссылки оформляются через единый класс `table-link-firm`, чтобы они выглядели как ссылки, но не спорили с кнопками;
  - `btn-link` использовать только для действительно вторичных действий, когда нужен минимальный визуальный шум;
  - нельзя смешивать в одной таблице несколько разных визуальных стилей ссылок без причины.

## 6. Порядок выполнения

1. Сначала вычистить `resources/sass/`:
   - `common.scss`,
   - `layout.scss`,
   - `form.scss`,
   - `template.scss`,
   - `crutches.scss`.
2. Затем пройти shell-страницы.
3. Затем public pages.
4. Затем admin/profile pages.
5. Затем legal pages.
6. Затем `resources/js/`.
7. После каждого крупного блока делать:
   - `make architecture`,
   - `make yarn-build`,
   - визуальную проверку ключевых экранов.
